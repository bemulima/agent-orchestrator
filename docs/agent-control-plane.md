# Agent Control Plane foundation

`agent-system/` is the canonical source for centrally managed agent behavior
assets in this repository. `internal/agentcontrol` loads and validates its
manifest, derives deterministic checksums, compares managed assets with a
target repository, and applies repository skill updates only when the caller
supplies the exact reviewed proposal fingerprint.

## Ownership

- **MANAGED** — canonical source is owned by this control plane. Distributed
  `.agents/skills/**` and `.agents/profiles/**` copies are tracked by
  `.agents/manifest.yaml`; edits that differ from the last managed checksum
  become conflicts and are never overwritten automatically.
- **LOCAL** — canonical truth remains inside the service repository. This
  includes `AGENTS.md`, `.ai/service.yaml`, `.ai/commands.yaml`, contracts,
  architecture facts, and testing metadata. The distributor does not write
  `.ai/**`.
- **GENERATED** — derived metadata or projections. The target
  `.agents/manifest.yaml` records managed provenance; existing
  `.ai/architecture/**/*.mmd` remains generated by the existing architecture
  subsystem and is unchanged by this feature.

Unlisted skills under `.agents/skills/**` are repository-local. Distribution
does not delete them or any managed asset that disappears from the canonical
catalog. It carries old provenance forward and reports retained entries.

## Sources and profiles

`agent-system/manifest.yaml` lists stable asset IDs, kinds, source and target
paths, versions, applicability and checksum mode. `checksum: computed` means
`internal/agentcontrol` hashes sorted relative file names and exact bytes using
SHA-256; the resolved digest is written to target provenance. No canonical
project/service `.ai` file belongs in `agent-system/`.

`task-route` finds evidence-backed architectural responsibility, concrete
targets, contracts and verification boundaries. It does not create task IDs or
the execution DAG. `contract-plan` records whether a future source contract
freeze is planned; `FREEZE_REQUIRED` is not proof that a source file exists or
has been frozen.

Architecture profiles include required repository shape, contract ownership
surfaces, import policy, composition surfaces, and verification strategies. Go
contracts are placed inside their owning route's declared `contract_surface`;
there is no universal `internal/contracts` fallback. Standard-library imports
are classified separately, same-module imports follow route dependency
direction, third-party imports need profile or `go.mod` evidence, and explicit
external-service prefixes remain distinct. A Go module and Go source alone do
not resolve `go.canonical`; its layered paths must be present. The
`nextjs.common` profile shares structural checks across its `student` and
`admin` policy variants. These checks use repository paths, not repository
names.

An approved plan keeps its project/repository-level `Task`. The `plan-shards`
command with `--plan-id <uuid>` prepares internal `ArchitecturalShard` records only for
responsibilities explicitly selected in the approved planner output. Shards
have deterministic IDs, narrow file scopes, local intent, contract references,
and a verification strategy. Composition work is marked serial for a later
phase. Runtime HTTP route and message consumer registration remain routing and
composition evidence; they do not imply a frozen source-interface contract or
a transport dependency on composition. Application and repository interfaces
continue through the normal contract freeze. No GitHub issue or PR is created per shard.

For `FREEZE_REQUIRED`, the current materializer writes deterministic,
behavior-free contract skeletons only at profile-owned locations. It rejects
traversal, symlink escapes, invalid module/package/symbol data, unsupported
imports, and protected-file collisions. The persisted execution baseline
records hashes, contract/profile fingerprints, approved Plan fingerprint, and
the original Git base revision. File validation alone does not freeze it. The
Contract Freeze pipeline snapshots the clean source, deterministic materializer
output, and final agent workspace separately as `MaterializerChanges`,
`AgentChanges`, and `BaselineChanges`. Deterministic orchestration computes all
three; the Contract Agent only claims its own delta and accepted materialized
paths. Scope checks, complete content verification, review, and the local
contract-only commit use the full `BaselineChanges`. A fixed profile
verification command and a separate read-only reviewer thread must also pass.
Post-commit checks bind the single-parent commit to the source revision and
persisted file hashes.

`FROZEN` and `READY_FOR_FANOUT` require complete persisted agent, verifier,
contract-check, reviewer, commit, fingerprint, and aggregate-hash evidence.
Every contract-dependent shard in a repository must use that repository's
same verified commit. Structured source-preflight records include the
repository path and project, expected and observed revisions, clean status,
repository identity, contract-baseline commit, outcome, reason, and bounded
inspection error. Confirmed source or contract drift invalidates the baseline
and blocks readiness. An inspection failure blocks the current fan-out
attempt, preserves a valid `FROZEN` baseline and `READY_FOR_FANOUT` evidence,
and allows a later inspection retry.
Readiness is persisted audit evidence and does not launch workers; the separate
`plan-shard-run` command starts the Temporal fan-out workflow. That workflow
schedules independent shard activities concurrently under the existing global
activity cap, persists attempts and the barrier, and only schedules deterministic
assembly after all required shards pass. This execution path is validated only
in the disposable `CANARY_ONLY` environment and is not production-ready.
Migration 018 and repository round-trip/down/up behavior are covered by the
disposable PostgreSQL integration test.

## Distribution and approvals

`agent-assets-plan --root <repo>` is read-only. It records the target Git HEAD,
asset states, checksums, deterministic diff and proposal fingerprint.
`agent-assets-apply` requires the owner to pass that exact fingerprint; it
recomputes the catalog and target state before writing. Writes are confined to
manifest-declared `.agents/**` paths and `.agents/manifest.yaml`. It does not
commit or push. Local modifications, unsafe symlinks and unrelated files are
preserved; conflicting managed paths block the entire apply.

Global policy uses a separate read-only path:
`agent-policy-plan --target <explicit-path>` compares an explicitly selected
file with `agent-system/global/AGENTS.md`. There is no global installer and no
server-startup write to `~/.codex/AGENTS.md`. Installation stays unavailable
until a dedicated high-trust approval and user-config adapter exist.

Only `course-dev-orchestrator` isolation code may manage Git worktree
lifecycle. Agents and workers must not create, move, remove, or manage
worktrees; they operate only in the workspace assigned by the orchestrator.

## Compatibility

The existing `.ai/agents/**`, `.ai/rules/common.md`, `.ai/workflows/**`,
`.ai/manifest.yaml`, and `.ai/template.yaml` remain in place. The embedded
`internal/onboarding/templates/v1` bundle continues to generate the legacy
common-rules copy; the new `agent-system/` assets are not read from those
legacy files. Migration is a later, separately reviewed step with this
intended mapping:

- `.ai/agents/**` role procedures can become conditional skills after ownership
  review; repository-specific constraints stay in local `AGENTS.md`/`.ai`.
- Shared procedural rules can move to `agent-system/global/AGENTS.md` or shared
  skills; local-only rules remain repository-owned.
- `.ai/workflows/**` procedures can become conditional skills, while task
  identity, execution DAGs, and Temporal coordination remain in the existing
  planning/workflow subsystems.
- `.ai/manifest.yaml` and `.ai/template.yaml` remain onboarding v1 compatibility
  inputs until a separately verified replacement preserves onboarding behavior.
- `.ai/service.yaml`, `.ai/architecture.yaml`, `.ai/contracts/**`,
  `.ai/commands.yaml`, testing metadata, and architecture Mermaid remain local
  repository facts or projections; they do not move into `agent-system/`.

Architecture manifest readers, Mermaid locations, renderer, auditor, and
onboarding behavior remain unchanged.

## Contract ownership without implementation routing

Profiles may declare ordered `boundary_ownership` rules with `owner_routes`
and `implementer_routes`. A compatible existing interface selects its concrete
path from repository evidence; otherwise the owner surface supplies the default.
A non-selected owner requires that explicit profile rule and source evidence.
Every Go consumer/implementer must have an allowed inward dependency on the owner.
Unknown owners, missing evidence and forbidden edges fail deterministic validation.

`ContractPlan.contract_owner_routes` is distinct from `RoutingResult.routes`
and `AffectedRoutes`, which remain implementation responsibilities. Each boundary
records consumers and its profile-derived implementers. An owner-only route does
not create a shard. Ownership, concrete path and implementer changes are serialized
into the ContractPlan and Plan fingerprints and therefore require fresh approval.

For go.canonical, the application boundary remains usecase-owned and the repository
port is domain-owned; persistence still cannot import usecase. Existing ports in
`internal/domain/repository/**`, `internal/domain/ports.go` or `internal/port/**`
resolve through profile/evidence, without a universal contracts directory. Other
explicit audited profiles may choose a different valid owner; this is not a rule
for every repository interface. Application-to-domain mapping belongs to the future
usecase worker, not this planning slice.

### Callable repository port completeness

Go repository-port references must resolve to an interface with at least one
exported operation signature. Empty interfaces and marker types fail both full
contract diff verification and committed baseline verification. Local embedded
interfaces and aliases are resolved in the contract file; opaque external
embeddings alone do not prove an operation. Independent review also checks
owner-owned input/output semantics. This does not permit SQL, concrete adapter
structs or executable method bodies in a contract-only diff. A callable interface
contract defines an API, while invoking a concrete adapter still requires an
implementation/test seam. Missing adapter methods are not PostgreSQL behavior RED.

### Replacement freeze and optional RED_SETUP

An INVALIDATED baseline is immutable historical evidence. The same unchanged
approved Plan may create a successor baseline through a fresh complete freeze.
The current projection selects the latest generation; historical IDs remain
retrievable. Replacing a terminal fanout requires a retired old baseline, a
frozen successor with matching task/project and no unfinished worker attempts.
Full prior fanout payload remains in audit.

Worker phase evidence records PREPARED, optional RED_SETUP, RED_VERIFIED,
IMPLEMENTING, GREEN_VERIFIED and VERIFIED. Missing persistence concrete seams
may receive a mechanically validated compile-only shell: pool field, constructor
and exact frozen methods returning explicit ErrNotImplemented. SQL and target
behavior are rejected. Setup sources and hashes are retained. RED changes only
approved tests relative to the setup snapshot; implementation starts only after
semantic RED is persisted. Existing callable seams skip setup.

RED agents prepare candidate behavioral tests; actual verification runs in the
orchestrator environment. A worker claim does not certify semantic RED. The
orchestrator accepts only an actual nonzero full-suite result with the explicit
semantic assertion marker and no compiler/fixture/environment errors, then
persists its own evidence before implementation. This preserves the isolated
agent environment without exposing database configuration.

A completed verified shard may be reused on retry only after exact canonical
package/approval/base checks, immutable single-parent commit verification, clean
workspace and frozen hashes, and fresh orchestrator GREEN reruns. Original
thread identity and timestamps remain unchanged; failed attempts remain history.
Independent integration rejection remains authoritative even when local checks
pass. Periodic review heartbeats prevent lease expiry from launching duplicate
model calls during a long read-only review.

## Disposable serialized composition canary

An approved composition shard remains outside worker fan-out. A persisted
BARRIER_READY precedes deterministic worker assembly and the separately typed
CompositionWorkPackage, bound to actual verified commits, frozen baseline,
approval fingerprint and parsed public APIs. Only approved composition files
are writable; layer source and frozen contracts remain read-only. The worker
prepares an empty router, proves semantic HTTP404 against a real PostgreSQL
fixture, then adds wiring. Orchestrator scope, hash, AST and uncached GREEN
checks precede its commit. A fresh final assembly replays worker commits in
stable order and composition last, before mechanical checks and a separate
read-only reviewer. This implementation remains CANARY_ONLY.
